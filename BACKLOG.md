  - **格式决策：按需围栏，不做全局转义。** 只在正文含结构行时才写一对 `<<< pokeclaw-body` / `>>> pokeclaw-body` 标记，围栏内按**逐字**读回。选它而不是「给每行加转义前缀」的理由有两条：转义是不可逆的猜（合法以 `\` 开头的正文会被误改，而老文件没有转义，读者无法区分「本来就带反斜杠」和「被转义过」）；围栏则是**无歧义**的——围栏内没有任何一行会被解释。选「按需」而不是「总是」的理由：普通对话的文件保持原样，人打开还是干净的 markdown，且不带围栏的读取路径每天都被走到，不会变成一条只在新文件上才跑的冷路。
  - **标记冲突**：若正文自身含标记行，则改用编号变体（`-1`、`-2` …）——否则围栏会被正文自己的文字提前闭合。有单测钉住。
  - **向后兼容**：老文件没有标记，读者照旧全盘接受（包括它们那些危险行——那是既有行为，不是新回归）。写入侧也无需迁移。

### Security — round 2 (2026-10-16, `docs/SECURITY_AUDIT_R2.md`)

Chose a source gate over a per-call confirm dialog because remote tasks have no foreground activity to show a dialog on — see the audit for why that split matters. `get_notifications` is deliberately left readable; tightening it is a separate decision. ## Task ledger, calendar, three-tier risk, scheduling — 部一 data line (2026-10-25)

One round landed the whole state/data track of the two-track plan: P0 contracts (`TaskSink` / `TaskRecord` / `CalendarGateway`), the M1 ledger (`TaskRecordStore` + `handleTaskEvent` dual-write + pure `TaskStateMachine`), M2.5 calendar (`CalendarGatewayImpl` over Instances + `calendar_read` + ContextFence), M2 approval semantics (`READ_ONLY`/`WRITE`/`DESTRUCTIVE` tiers, `WAITING_CONFIRM`, destructive never earns a remembered yes), and M4 scheduling (`ScheduledTaskStore` + AlarmManager + the reserved `schedule_task` trio + a visible queue). Tests 363 → 487. QA H60–H64 pending on device. Known boundaries, all deliberate:

- [ ] **P1 — M1 boundary: channel-initiated tasks are not in the ledger.** The dual-write sits in `TaskFlowController.handleTaskEvent`, so Telegram/Discord/WeChat/QQ/Douyin tasks (which enter via `ChannelSetup` → `TaskOrchestrator` without any UI callback) leave no `task_records.json` entry. Moving the write point into the orchestrator's event emission is the fix, but that file is owned by neither track — do it as its own change when the queue work next touches `TaskOrchestrator`, not as a drive-by.
- [x] ~~**P1 — scheduled tasks ran as `Channel.LOCAL`, so a fired task held every tool.**~~ — done 2026-10-26. A fired task now runs as `Channel.SCHEDULED`, which is unwatched for the same reason `Channel.EXTERNAL` is (R3-01), so `ToolRiskPolicy` holds it to the READ_ONLY ceiling: it may observe and answer, and the answer arrives as a notification. `make_call`, `system_key`, `send_message`, `input_text`, `schedule_task` and the rest are refused with a reason written for the model to repeat to the user ("tell the user this part needs to be run from the PokeClaw app while they are present"), not one that says "retry". Before this, a 07:30 brief whose agent loop reached for `system_key(key="enter")` would have pressed the key that approves system dialogs with nobody awake to see it. `ScheduleDispatcher.fireNow` passes the new channel to both the ledger and the orchestrator; `TaskSessionStore.autoReturnToChat` stays false so a fired task never yanks the user home. Tests 487 → 491.
- [ ] **P2 — the scheduled ceiling is READ_ONLY, and that is a product decision not yet made.** The fix above chose the strict ceiling because it is the safe default, not because someone decided what a brief should be allowed to do. The live casualty is `send_message`/`reply_via_notification` (WRITE): "at 07:30 text my wife that I'm running late" is refused today, and the model says so instead of doing it. Relaxing to a WRITE allowlist for scheduled tasks is the obvious follow-up — pick the tools by name, keep `make_call`/`system_key`/unclassified out, and add a QA case per tool let through. - [ ] **P2 — `calendar_create` is classified but not registered.** Its WRITE-tier entry and wait-after exemption are in place; the registration line lands with the UI track's class per the ownership handoff (部二 writes the tool, 部一 registers it).
